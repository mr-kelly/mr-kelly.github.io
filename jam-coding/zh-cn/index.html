Coding Agent 时代的人类时间编排

Jam Coding

AI 在写代码的时候，人该去哪里？
正确答案很少是「坐在屏幕前面看着它写」。

一份公开方法论 · Kelly Peilin Chan · 2026 年 8 月

选择今晚的 5 分钟套餐 ↓

定义

什么是 Jam Coding

Jam Coding
把 Coding Agent 的执行时间，当成一段需要提前编排的人类时间，而不是一段需要熬过去的空档。

名字来自乐队的 jam session。乐手不会在别人 solo 的时候干瞪眼——他在听，在伴奏，在准备下一个段落。人和 agent 的关系也一样：你们轮流出声，谁都不该在对方演奏时呆坐着。

起点

瓶颈已经不在「写」，而在「等」

Coding Agent 把一件事彻底改变了：写代码这个动作，从需要你全程在场，变成了一次可以派出去的任务。一次任务跑 3 分钟、20 分钟、两个小时，都是常事。

于是一个上一个时代不存在的问题冒了出来——这段时间，你这个人在干嘛？

大多数人没有答案，所以就地取材：盯着输出滚动，或者掏出手机。前者让你在任务结束时已经耗光了注意力，后者让你回到代码时要重新爬一遍上下文。两条路都是在把机器省下来的时间，还回去。

Jam Coding 的主张只有一句：机器工作的时间，应该在派出任务之前，就被分配给一件确定的人类活动。而在绝大多数时候，那件活动最好发生在离屏幕很远的地方。

原则

三条规则

  1. 只派出「可以离开的任务」

    一个任务如果没写清楚「做完长什么样」，你在路上就会开始不放心，然后掏手机。可离开的任务有三个特征：有明确的验收标准、有足够的权限自己跑完、失败了你能整个扔掉。写清楚这三件事的成本，通常不超过两分钟。

  2. 时间块归你，不归 agent

    不是「它跑多久我就等多久」，而是先看它大概要跑多久，再决定这段时间你去做什么。20 分钟的任务对应一段 20 分钟的人类活动——散步、一组训练、一次洗澡。任务的时长是输入，你的安排是输出，顺序不要反。

  3. 回来先看结果，不看过程

    不要回放它的输出流。先把东西跑起来看行为，再读 diff，最后才读它给自己写的总结。反过来的顺序会让你先被结论说服，然后带着结论去读代码——那时候你已经不是在审阅了。

时长是估的，估不准也没关系——重点是你在派出任务之前，就已经决定了自己这段时间去哪。宁可估短：任务比预期跑得久，你多得一段时间；你比预期回来得晚，也不会有任何损失。

场景协议

健身房协议

健身房版本不是一口气练完整场，而是一个循环：给 agent 派一个任务，训练 5、10 或 15 分钟，回来审阅和回复，再派下一轮、继续练。几个短节拍累积起来，就是今天的训练。

跑步机 · 5 分钟

三轮短跑走间歇

第一轮先短一点：把心率提起来，但不用让 agent 长时间等你。

05:00
    倒计时结束 先把跑步机减速再下来。回到 agent，审阅结果、回复，然后选择下一轮。

    出发前 · 90 秒

    确认这是一个你能走开的任务

    • 代码在独立分支上，或者已经 commit——你要能随时把这次结果整个扔掉
    • 任务写成「做完长什么样」，不是「帮我改一下」
    • 权限一次给足：能跑测试、能装依赖。半路问你要权限的任务，会把你叫回来
    • 通知只留一条：任务完成。其余全部静音

    每个节拍结束时

    回来，做决定，再离开

    • 还在跑 → 再选一个 5 分钟节拍，别站在原地盯着
    • 停下来问问题 → 回答它，并在发出回复前选好下一个节拍
    • 已经完成 → 坐下或站稳再审阅，派出下一项任务，从第一个没做完的动作继续
    • 手里拿着重量时，绝不读 diff，也不改 prompt

    回来之后 · 顺序很重要

    先看行为，再看改动，最后才看它怎么说

    • 第一步：跑起来。跑测试，或者直接把应用打开用一下
    • 第二步：读 diff。它到底改了什么，改了哪些你没让它改的
    • 第三步：才读 agent 的总结。它是全场最擅长自我美化的那一个

    人类段落

    这段时间里，只有人能做的三件事

    如果你实在离不开工位，那就把这段时间花在下面三件事上。它们的共同点是：agent 再强也接不走。

    定义「做完长什么样」

    Agent 能写代码，不能替你决定什么叫做对了。验收标准永远是人类的活，而且写验收标准这件事，恰好最适合在等待的时候做——它需要的是判断力，不是键盘。

    和真实的人说话

    给用户打个电话，去问同事一个问题，回一封拖了三天的邮件。没有任何 agent 能替你完成一次真实的对话，而你的下一个需求多半来自其中一次。

    判断这个东西该不该存在

    Agent 会把你交代的一切都实现出来，包括不该被实现的那些。「砍掉这个功能」的念头，从来不会由它主动提出。

    而在这三件之外，请优先选择离开屏幕的那一项。你的身体是这套系统里唯一不能外包的基础设施——模型会换代，键盘会换，那副身体不会。

    示例

    一天的样子

    • 09:10派出 第一个任务，估 20 分钟 · 你 下楼买咖啡，走一圈
    • 09:35回来：跑测试 → 读 diff → 提一轮修改，估 6 分钟 · 你 一组深蹲
    • 09:45合并。趁热写下第二个任务的验收标准
    • 10:00派出 重构任务，估 70 分钟 · 你 去健身房
    • 11:15回来：先跑起来看行为，两处不对，拆成两个小任务
    • 12:00你 午饭。不带手机
    • 14:00你 只有人能做的事：给三个用户打电话
    • 16:30派出 隔夜的批量迁移 · 你 下班
    • 次日睡饱了再读结果。它等了你一夜，不差这十分钟

    反模式

    四种把等待时间还回去的方式

    保姆式盯屏

    你在读一串 token。token 流不是产出，是过程；真正的产出是 diff 和跑起来的东西，而它们只在结束时才存在。盯着看不会让它跑得更快，只会让你在它跑完、真正需要你判断的那一刻，已经先累了。

    人肉调度器

    同时开了六个 agent 之后，你的工作就变成了在六个 agent 之间做上下文切换。上限从来不是算力，是你的审阅带宽——判断标准不是「我能开几个」，而是「我能认真读完几份 diff」。多数人是两到三个。

    债务螺旋

    「反正等着也是等着，再开一个任务吧。」但每一个新任务最后都会变成一份等你审阅的 diff。派出任务几乎不花时间，审阅才花时间——用等待去换更多待审，是在给未来的自己借债。

    刷手机漂移

    切去社交媒体的代价不是那几分钟，是回来之后的注意力残留：重新爬回代码上下文所需的时间，常常比 agent 这次跑的时间还长。而且你回来时，比走的时候更累——这是它和散步、训练、洗澡之间最本质的区别。

    FAQ

    常见问题

    Jam Coding 和 Vibe Coding 是一回事吗？

    不是，两者管的是不同的一端。Vibe Coding 讲的是你怎么把活交出去——怎么描述需求、怎么让 AI 写出能用的东西。Jam Coding 讲的是活交出去之后，你这个人怎么过这段时间。一个管输入，一个管人。

    和番茄钟有什么区别？

    番茄钟假设人是执行者：人专注 25 分钟，休息 5 分钟。Jam Coding 里执行者是机器：机器专注，人恢复，比例正好反过来。而且时长由任务决定，不由计时器决定——没有哪个 agent 会因为你的闹钟响了就停下来。

    一次同时跑几个 agent 合适？

    从 1 个开始。上限不是算力，是你的审阅带宽。判断标准不是「我能开几个」，而是「我能认真读完几份 diff」。对多数人来说是两到三个。

    这不就是给摸鱼找借口？

    摸鱼是无计划地逃离一件正在进行的事；Jam Coding 是事先编排一段你本来就无法用于深度工作的时间。判据有两条：这段时间是不是在派出任务之前就决定好的；回来的时候你是不是比走之前更清醒。两条都成立，它就不是摸鱼。

    Agent 中途卡住了怎么办？

    卡住是常态，所以功夫全在出发前：足够的权限、明确的验收标准、能自己跑测试。如果一个任务平均每 5 分钟就要问你一次，它就还不是一个可以离开的任务——先把它拆小。

    需要什么工具？

    不需要专门工具。一个能在后台跑完整任务的 coding agent，加一块表。难的从来不是工具，是允许自己在机器工作的时候离开。

    它跑得越久，你就该走得越远。
