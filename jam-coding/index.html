Scheduling human time in the coding agent era

Jam Coding

Where should you be while the AI writes code?
The answer is almost never "in front of the screen, watching it write."

An open practice · Kelly Peilin Chan · August 2026

Definition

What Jam Coding is

Jam Coding
Treating a coding agent's run time as human time that gets scheduled in advance, rather than a gap you have to sit through.

The name comes from a band's jam session. No musician sits and stares while someone else takes a solo — they listen, they comp, they set up the next passage. You and the agent work the same way: you take turns making sound, and neither of you should be idle while the other plays.

The premise

The bottleneck moved from writing to waiting

Coding agents changed one thing completely: writing code went from something that needs you present the whole time to something you can send off. A single task running 3 minutes, 20 minutes, or two hours is now unremarkable.

Which surfaces a problem that didn't exist a few years ago — what is the human doing during that time?

Most people have no answer, so they improvise: they watch the output scroll, or they reach for their phone. The first burns your attention so that it's already gone by the time the run ends. The second means re-climbing the whole context when you return. Both hand back the time the machine just saved you.

Jam Coding makes one claim: the machine's working time should be assigned to a specific human activity before you launch the task. And most of the time, that activity is best done far away from the screen.

Principles

Three rules

  1. Only launch leavable tasks

    If a task doesn't say what done looks like, you'll start feeling uneasy on the way out and reach for your phone. A leavable task has three properties: a clear definition of done, enough permission to finish on its own, and a failure mode where you can throw the whole thing away. Writing those three down rarely takes more than two minutes.

  2. The block belongs to you, not the agent

    Not "it runs, so I wait." Estimate roughly how long it will take, then decide what you'll do with that time. A 20-minute task earns a 20-minute human activity — a walk, a training block, a shower. Task length is the input; your schedule is the output. Don't reverse it.

  3. Read the result, not the reel

    Don't replay the output stream. Run the thing first and watch its behavior, then read the diff, and only then read the summary the agent wrote about itself. In the reverse order you get convinced by the conclusion first and then read the code holding it — at that point you're no longer reviewing.

The Jam Chart

Solo10–30 min A whole feature, a medium refactor, an end-to-end run Walk around the block, take a shower, do a full training circuit. Don't use the window to launch a second and third task
Set30–120 min A large migration, the full test suite, deep research A full gym session, the commute, a real meal, a 20-minute nap. Don't check back every five minutes — that means you never left
Overnight2 hours+ Batch jobs, long evaluation runs, overnight work Sleep. It's the one beat where the activity isn't optional. Don't set an alarm to check the results at 3am

The estimates are estimates, and being wrong is fine — what matters is that you decided where you'd be before you launched. Err on the short side: if the task runs longer than expected you gain time, and if you come back later than planned, nothing is lost.

Field protocol

The gym protocol

The gym is Jam Coding's best partner because it's already segmented: a set, a rest, the next set. That rhythm lines up almost exactly with how agent tasks run. It's also the easiest place to ruin both activities — pull out your phone to tweak a prompt mid-session and you'll do neither well.

Before you leave · 90 seconds

Confirm this is a task you can walk away from

  • Work is on its own branch, or committed — you need to be able to throw the whole result away
  • The task states what done looks like, not "clean this up for me"
  • Grant permissions up front: run tests, install dependencies. A task that stops to ask for access is a task that calls you back
  • Leave exactly one notification alive: task finished. Mute everything else

Between sets · 40–90 seconds

One permitted action: glance at the status

  • Still running → put the phone down and start the next set
  • Stopped with a question → answer in one line, or reply "skip it, I'll handle this when I'm back"
  • Don't read the diff. Reading a diff takes working memory and so does a heavy squat; run them together and you do both badly
  • Never rewrite a prompt under a loaded barbell

When you're back · order matters

Behavior first, changes second, its own account last

  • Step one: run it. Run the tests, or just open the app and use it
  • Step two: read the diff. What did it actually change, and what did it change that you never asked for
  • Step three: only now read the agent's summary. It is the most flattering narrator in the room

The human track

Three things only a human can do with that time

If you genuinely can't leave your desk, spend the block on these three. What they share is that no agent, however capable, can take them off your hands.

Define what done looks like

An agent can write the code; it can't decide for you what counts as correct. Acceptance criteria stay human work — and writing them is the perfect thing to do while waiting, because it needs judgment rather than a keyboard.

Talk to an actual person

Call a user, ask a colleague the question you've been sitting on, answer the email that's three days old. No agent can hold a real conversation on your behalf, and your next requirement probably comes out of one.

Judge whether the thing should exist

An agent will faithfully build everything you ask for, including the parts that shouldn't be built. "Let's cut this feature" is a thought it will never volunteer.

And when any of these compete with leaving the screen, leave the screen. Your body is the one piece of infrastructure in this system you can't delegate — models get replaced, keyboards get replaced, that doesn't.

Example

What a day looks like

  • 09:10Launch first task, est. 20 min · You go get coffee, walk a loop
  • 09:35Back: run tests → read diff → send one round of fixes, est. 6 min · You do a set of squats
  • 09:45Merge. While it's fresh, write the acceptance criteria for the next task
  • 10:00Launch the refactor, est. 70 min · You go to the gym
  • 11:15Back: run it and watch the behavior. Two things are wrong; split them into two small tasks
  • 12:00You eat lunch. Leave the phone behind
  • 14:00You do the human-only work: call three users
  • 16:30Launch the overnight migration · You go home
  • Next dayRead the results after a full night's sleep. It waited all night; ten more minutes won't hurt

Anti-patterns

Four ways to hand the time back

Babysitting

You're reading a stream of tokens. The stream isn't the output, it's the process; the real output is the diff and the running thing, and neither exists until the end. Watching won't make it faster — it just means that at the moment it finishes and finally needs your judgment, you've already spent it.

The human scheduler

Once six agents are running, your job has become context-switching between six agents. The ceiling was never compute, it's your review bandwidth — the question is not "how many can I launch" but "how many diffs can I read carefully." For most people, two or three.

The debt spiral

"I'm waiting anyway, might as well start another one." But every new task eventually becomes another diff waiting for your review. Launching costs almost nothing; reviewing costs everything — trading idle time for more pending review is borrowing against your future self.

Doomscroll drift

The cost of switching to social media isn't those few minutes, it's the attention residue afterward: the time to climb back into the code context is often longer than the agent's run itself. And you return more tired than you left — which is the fundamental difference between it and a walk, a training set, or a shower.

FAQ

Common questions

Is Jam Coding the same as vibe coding?

No — they cover opposite ends of the same handoff. Vibe coding is about how you hand the work over: how you describe intent and get the AI to produce something usable. Jam Coding is about what happens to you after the work is handed over. One governs the input, the other governs the person.

How is it different from the Pomodoro Technique?

Pomodoro assumes the human is the executor: you focus for 25 minutes, then rest for 5. In Jam Coding the machine is the executor — the machine concentrates and the human recovers, which inverts the ratio. And the length comes from the task, not from a timer: no agent stops because your alarm went off.

How many agents should I run at once?

Start with one. The ceiling isn't compute, it's your review bandwidth. The question is never "how many can I launch" but "how many diffs can I actually read carefully." For most people that's two or three.

Isn't this just an excuse to slack off?

Slacking off is unplanned escape from work in progress. Jam Coding is a pre-scheduled use of time you could not have spent on deep work anyway. Two tests: was the activity decided before you launched the task, and do you come back sharper than you left? If both hold, it isn't slacking.

What if the agent gets stuck while I'm away?

Getting stuck is normal, which is why the work happens before you leave: enough permissions, a clear definition of done, and the ability to run its own tests. If a task interrupts you every five minutes on average, it isn't a leavable task yet — break it down first.

What tools do I need?

None in particular. A coding agent that can run a whole task in the background, and a watch. The hard part was never tooling — it's giving yourself permission to leave while the machine works.

The longer it runs, the further you should go.
