最近，一位负责大团队的朋友问我：大家已经在用 AI，也在把经验写成 Skill，接下来该怎么让整个团队真正用起来？

Agent 是能按目标读取资料、调用工具并连续办事的 AI 助手；Skill 是给它处理某类任务的工作说明书。他举的例子是：做促销活动的同事，把熟悉的步骤写下来，让别人和 AI 接着用。

这有价值。但他接着问：团队里有多少人，是否就要有多少 Skill、多少 Agent？是否先按真人团队分组，再把 Skill 一层层汇总？

这恰好是团队落地 AI 时最容易走进去的路：先数人，再数 Agent，接着数 Skill。

先画组织图：销售 Agent、运营 Agent、设计 Agent、主管 Agent。再细分岗位、增加 Skill、安排汇报。最后还得有个人派活、催进度、整理回答。

这个人，通常就是你。

不妨先问三个问题：

**你问项目进展时，Agent 能找到已记录的事实吗？**

**下一位同事能只凭 Skill 完成任务吗？**

**几个 Agent 都说完成了，谁来核对依据？**

这也是我以前说过的**“超级打工人陷阱”**：AI 看起来分担了很多活，最后所有交接仍要经过一个人。

> **AI 产出 = 能力 × 授权 × 验收**

所以，问题往往不是 Agent 不够多、Skill 写得不够勤。恰恰相反：你把人的分工原样搬进去，却没有把资料、权限和完成标准交给系统，协调工作反而留给了自己。

**Agent 的岗位可以借用，人的组织图不能照搬。**

## 为什么“给 Agent 分岗位”还不够？

我以前也讲过，要像管理员工一样，给 Agent 明确职责。这个比喻是有用的：它让人停止零散提问，开始说明什么任务可以交出去、什么情况必须回来找人。

但比喻走得太远，就会误导我们。

真人组织图解决的是人的时间、专业分工和管理责任。Agent 的工作边界首先取决于它能读取的资料、能调用的工具、被授予的权限，以及谁会检查结果。给 Agent 起一个岗位名，并没有配置好这四件事。

真人员工在同一家公司，会参加会议、了解业务变化，也能主动找人核对。Agent 不会因为名字叫“运营主管”，就自动知道最新促销方案；也不会因为另一个 Agent 叫“设计专员”，就自动获得它的文件和判断依据。

你在屏幕上画出一条汇报线，并没有给它们建立共同事实。

这就是为什么“为每个人配一个 Agent，再让每个人每周交一个 Skill”不等于公司形成了 AI 能力。个人可能确实做得更快，经理仍可能要向每个人收集进展；一个 Agent 做出了结果，下一个 Agent 仍要重新听一遍项目背景。

这不是说分工和 Skill 没用。问题在于把**数量**当成了完成标准。

一个促销 Skill 是否有价值，不看它有没有按周交上来，而看下一次促销时，另一个获授权的人能不能按它取到正确资料、跑通任务，并看懂哪些地方要人工确认。

**Skill 写了多少，不等于工作能传下去。**

对使用者来说，Skill 还是一个与 Agent 交互、触发它处理某类工作的入口。人要看懂名字，判断眼前的事该用哪一个；有时 Agent 也要根据任务选择合适的 Skill。入口一多、名字又相近，光是“该用哪个”就变成一项新工作。

结果可能很反直觉：目录里的 Skill 越多，真正被调用的比例反而越低。常用的还是那几个，其他 Skill 写完就躺在列表里；遇到不确定的任务，大家干脆回到聊天框，从头解释一遍。**入口越多，不等于使用越多。**

数量还会带来一笔常被漏算的账。每增加一个 Agent，就要决定它能看哪些资料、用哪些工具、和谁交接、出错时谁复核。每增加一个 Skill，就要有人维护适用条件、资料版本和验证结果。它们如果只是在目录里增加名字，团队得到的是更多交接点，不是更多完成的任务。

更麻烦的是，岗位越细，同一份事实越容易被重复讲述。活动日期改了，几个 Agent 各自拿着旧说明做事；某个 Skill 更新了，其他 Skill 还引用旧流程。你不得不再设一个“主管 Agent”检查它们。看起来是在自动化管理，实际上只是把原来的沟通成本换了个界面。

先减下来，是为了让这笔账可见。暂停按人数配 Agent、按周数交 Skill 的扩张，拿一个任务试出最低够用配置；遇到明确的能力或权限边界，再增加。**少不是目标，够用且能交付才是目标。**

## 怎样算出够用的数量？

先从组织图退回到一个真实问题。

比如负责人每周都会问：“这次活动准备到哪一步？还有哪些风险？下周谁要处理？”

照搬组织图的做法是：让几个 Agent 分别扮演策划、运营、设计和主管，逐个询问，再由一个 Agent 汇总。每个角色如果持有不同版本的活动资料，最后还得由你核实哪一个说法是新的。

从任务出发则简单一些：先确定项目记录在哪里，最新状态由谁维护，现有 Agent 可以读哪些资料，回答里必须带哪些来源，哪些判断要由负责人签收。它能回答，就暂时不需要为这一个问题新增 Agent。回答错了，再看是事实没更新、权限没给、方法没写清，还是确实需要另一种执行能力。

回到上面的公式，三项分别对应三件事。

**能力：让执行者拿到可用的方法。** 模型本身会写总结，但不知道你公司的活动流程。把经常重复、经过验证的步骤保存成 Skill 或工作指引，连同适用条件和例外一起写清楚。它是做事的方法，不是为了凑一个“虚拟岗位”。

**授权：让执行者接触到该用的事实。** 项目状态、负责人、时间、决策和阻塞项需要有可查的记录，并按角色开放。AI 能不能回答，取决于相关资料是否被记录或连接、是否还有效、它是否有权读取。连接一个 Agent，不等于自动读取所有人的私人聊天和本地文件。

**验收：让结果有明确的出口。** 一份进展答复至少要指出依据、更新时间、缺失信息和待人确认的风险。Agent 可以整理和起草，业务负责人负责判断是否准确；对外承诺、改动正式记录或上线，仍由有权限的人批准。

你会发现，三项里没有“Agent 数量”，也没有“Skill 数量”。先用现有工具完成这项任务，再看缺口在哪里。现有 Agent 没有执行某个必要动作的工具或权限，才考虑补充另一个合适的 Agent；重复步骤总要靠人解释，才考虑把它写成一个经过验证的 Skill。根据工作需要，最后可以是一个 Agent，也可以是多个。

## 什么时候再把 Agent 和 Skill 加回来？

当任务确实需要并行处理、不同工具或权限、相互独立的专业判断，多个 Agent 很有用。比如研究资料与核对数据可以并行，写入正式记录的 Agent 可以只拥有提议权限，审核由另一个有责任的人完成。

增加一个 Agent，应该回答“它解决了哪一种不同的工作或边界”，而不是“组织图上还有哪个位置空着”。

增加一个 Skill，也应该先过三道检查：这件事是否重复出现？使用者能否说清何时触发它，Agent 能否识别适用条件？换个人调用，能否按同一标准完成并复核？同一流程已有多个版本，就先合并；只换了客户或活动资料，就更新资料，不必复制一份新 Skill。

答不上来，就先别给它起一个很响亮的名字。没人能执行的“专家 Skill”，放进目录里也只是多了一份需要人维护的文档。

## 如果这个团队要试，我会怎样开始？

我不会让整个团队先改工具，也不会要求大家一夜之间删除已有 Skill。第一周先暂停以数量为目标的新增，盘点同类 Skill 中哪些只是资料不同、哪些真的有不同的工作方法；再看哪些被人找到、实际调用并完成过任务。没有调用记录的，就标作未知，不把上传数量当成利用率。然后只挑一个负责人确实会反复追问、资料又相对清楚的问题，例如某项活动的每周进展。

先让业务负责人写下五个字段：当前状态、下一步、负责人、截止时间、风险。把已经存在的资料整理到一个获授权的共享位置，标出每条记录从哪里来、由谁更新。需要私下处理的谈话和文件留在原处，不因为要用 AI 就全部搬进去。

再选现有的一个 Agent 提问：“依据本周记录，活动进行到哪里？哪些事项没有负责人或缺少更新？”让它给出带来源的草稿，并清楚标出“不知道”，不要把空白编成结论。

最后由负责人核对一次。若发现它频繁误解“延期”“已完成”等状态，才把这类重复规则写进 Skill；若发现数据本身没人更新，先解决记录责任，继续增加 Skill 不会有帮助。若现有 Agent 已能完成读取和整理，也没有理由仅为了“组织完整”再配一个主管 Agent。

这一步**什么算完成**？同一个问题，下周由另一位获授权的同事发问，也能从最新记录得到可追溯的答复；负责人只需核对例外和作出决定，而不是重新向所有人收集基础事实。若试点中用不到某个 Agent 或 Skill，就暂时不把它算进这条流程；做不到，就如实记录缺了哪份资料、哪个负责人、哪条授权。

交付时留一份很朴素的证据包：**原问题、资料缺口与根因、改了哪些记录或指引、两次提问的验证结果、实际操作画面、未解决的风险、签收人。** 没有这些，演示时答对一次，也还不能算可用。

## Busabase 在这里负责哪一层？

聊这件事时，朋友也问我，现有员工使用的 Agent 界面和 Busabase 到底是什么关系。

Busabase 是给团队和已连接 Agent 共用的业务资料与工作记录底座。它可以保存结构化的业务记录、文档、文件、Skill 和提示词；Playbooks 帮助团队找到可复用的方法，权限和变更请求让团队决定谁能读、谁能提议、谁能直接写入。它并不要求每位员工放弃正在使用的 Agent 界面。

对负责人来说，先要的也不是“一个 Agent 管全部人”。先让现有 Agent 能在授权范围内读到同一份可信记录，并让人看得到答案依据。Busabase 的 Insights 可以查看**记录在这个工作空间内**的变更、提案和贡献；它不是对员工所有私人 AI 活动的实时监控。

如果资料不进来、没人维护、权限没设好，底座也不会凭空知道公司的进展。反过来，一旦团队能围绕同一份事实工作，换用不同 Agent 时，就不必把每次对话都从零讲起。

我不会承诺“一套平台加一个 Agent，替代所有岗位”；更不会在没看过流程和权限之前，让团队把内部资料全部倒进去。所谓“先减下来”也不是裁掉人或清空已有资产，而是停止让 Agent 与 Skill 的数量代替交付判断。产品能提供共享的位置，什么值得共享、什么必须隔离、谁对结果负责，仍是管理决定。

## 这件事最终由谁负责？

我做过 CTO，也负责过跨部门项目推进。现场最费力的部分，通常不是把岗位画出来，而是让目标、资料和验收在不同人之间接得上。AI 把这个问题放大了：生成结果变快，交接不清却更容易被藏起来。

如果团队缺的是持续确定优先级、跨部门推进和签收结果的人，CAIO Office，也就是企业 AI 转型与执行办公室，负责把这些管理动作持续做下去。若缺的是可共享的业务记录和方法，就先整理企业 AI 资产；Busabase 可以承载其中的资料、Skill 和变更记录。具体配置仍由业务问题、现有工具和权限要求决定。

你现在就可以做一个自查：找出上周你亲自催过的一项进展，暂时不增加 Agent 和 Skill，只写下它的资料入口、可执行的方法、读取与修改权限、完成证据和签收人。缺哪一项，就先补哪一项。

**Agent 和 Skill 的数量，不是交付能力。**

**少画一张组织图，多留一份可接手的记录。**

带着这一项真实任务和现有记录来，我们再判断需要多少 Agent、哪些 Skill，以及 Busabase 是否适合做它们共用的底座。
